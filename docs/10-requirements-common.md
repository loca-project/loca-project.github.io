# Loca 要件定義 (1) 全体アーキテクチャ・共通要件

> 移植元: Loca システム要件定義書 1章。サイト名と、プラットフォーム非依存化にともなう
> 変更点は本文中に「Loca での扱い」として注記した。

## 1. 全体アーキテクチャ・共通要件

### 1.1. 認証・ユーザー権限
* **認証方式**: Google認証のみを実装する。
* Firebase Authenticationの標準動作に準拠し、明示的なログアウトがない限りセッションを永続保持する。
* **認証の実行**: Google認証は**プロフィール登録時のみ**実行する。それ以外の操作ではGoogle認証を行わない。
* **初回認証時の挙動**: ユーザーが初めてGoogle認証を行う場合（サイトにプロフィール情報が未登録の場合）は、**プロフィール登録画面**を画面中央に表示する。プロフィール登録画面には、「登録」と「キャンセル」の操作項目を画面下部に配置する。
* **2回目以降の認証挙動**: 既にプロフィールが登録されている場合、Google認証のアイコンクリック時、プロフィール登録画面は表示せず、認証を完了する。
* **認証UI**:
    * 画面右上にユーザーアイコンを表示する。
    * **アイコン操作**: アイコンをタップした際にポップアップを表示し、その中に「**プロフィール**」と「ログアウト」ボタンを配置する。
    * **管理者モードの追加**: 認証済みユーザーが**管理者権限を持つ場合**、ポップアップ内に「プロフィール」の下に「**管理者モード**」のボタンを**追加で表示**する。
* **権限によるUI制御**:
    * **未認証ユーザー**: 「登録」および「編集」モードへ遷移するUI操作（地図クリックや既存マーカークリック）を無効化または非表示にする。
    * **認証済みユーザー**: 登録・編集操作が可能。
    * **管理者ユーザー**: 上記に加え、「管理者モード」へのアクセスが可能となる。
* **プライバシー**:
    * 動画はすべてYoutubeリンクとして扱い、個人情報やサイト自体に個別のデータを登録しない。
    * データを最大限保存しない設計とする。
* **同意履歴の記録**: プロフィール登録時、**ユーザーが同意した日時**をサイト側で記録する。

### 1.2. システム構成・ファイル設計
* **JSファイル構成**:
    * サイドメニュー（各タブ共通処理）は独立したJSファイルとする。
    * ランキング処理は独立したJSファイルとして共通化する。
    * **検索・ランキング処理の分離**: 「マーカー検索」と「ランキング適用」は要件（表示制限の有無）が異なるため、**プログラム（ロジック）を明確に分けて実装**する。ランキングのロジックは既存を維持し、マーカー検索は新規に実装する。
    * 都道府県、撮影機器（メーカー・シリーズ・モデル）の定義は、ソース編集なしで更新可能な独立したJSファイルとする。
* **セキュリティ・API設計**:
    * **環境変数定義 (.env)**: API KeyやFirebase、Google Maps IDの変数は、以下の内容で**.envファイルにまとめ**、**コードは必ず変数から値を取得**して利用する。
        ```
        # .env
        # --- API KEY (すべてのサービスで共通) ---
        VITE_COMMON_API_KEY="ダミー"
        # --- Firebase Config ---
        VITE_FIREBASE_API_KEY="${VITE_COMMON_API_KEY}"
        VITE_FIREBASE_AUTH_DOMAIN="ダミー"
        VITE_FIREBASE_PROJECT_ID="ダミー"
        VITE_FIREBASE_STORAGE_BUCKET="ダミー"
        VITE_FIREBASE_MESSAGING_SENDER_ID="ダミー"
        VITE_FIREBASE_APP_ID="ダミー"
        VITE_FIREBASE_MEASUREMENT_ID="ダミー"
        # --- Google Maps API ---
        VITE_GOOGLE_MAPS_API_KEY="${VITE_COMMON_API_KEY}"
        VITE_MAP_ID=="ダミー"
        # --- YouTube Data API ---
        VITE_YOUTUBE_API_KEY="${VITE_COMMON_API_KEY}"
        ```
    * **.gitignore**を作成し、.envファイルを利用者が閲覧できないようにする。
    * **APIコール方針**: 可能な限りAPIのコールはサーバー側で行い、クライアントからのAPIのコール数を減らす設計とする。
* **パフォーマンス最適化（バンドルサイズ）**:
    * **目的**: メイン画面（地図）の初期表示速度を向上させ、パフォーマンス警告を解消する。
    * **バンドルサイズの制限**: 圧縮後のチャンクサイズが**500kB**を超えないことを目標とする。
    * **Google Maps API**は無理に分割せずメインバンドル（またはReactベンダーバンドル）に含める。
    * **Firebaseの初期化**エラーを防ぐため、バンドラーのデフォルト挙動（またはメインバンドルへの統合）に任せる。

### 1.3. バックエンド処理・API制限
* **定時データ更新**:
    * **頻度**: 1日1回、毎日00:00 JSTに実行。
    * **方法**: cronジョブやFirebase Functionsなどのサーバーレス機能を使用。
    * **内容**: Youtube APIを経由してすべてのマーカー情報を更新する。
    * **エラーハンドリング**: 更新失敗時は15分おきに3回リトライし、最終的に失敗した場合はログを出力する。
* **APIレートリミット**:
    * すべてのAPI処理に対し、バウンズとレートリミットで不正実行を制御する。
    * 具体的な制限（例：IPアドレスあたり10回/分）を定義する。
    * **制限到達時のエラーメッセージ**: 操作が制限されています。短時間のうちに連続して操作したため、一時的に制限がかかっています。10分ほど待ってから再度お試しください。

### 1.4. マーカーデータ読み込みのリアルタイム・ハイブリッド化と軽量化 (変更)
* **目的**: **APIコストを抑えつつ、リアルタイム性を確保**してマーカーの即時表示を解決する。初期表示の高速化と、直近の変更を即座に反映する。
* **書き込みの軽量化（Soft Deleteの採用）**:
    * **CRUD操作**: 登録・更新・削除時には、Firestoreへの**1件分の書き込みのみ**を実行する。JSONファイルの**再生成（全件処理）は行わない**。
    * **削除処理**: マーカーの「削除」は、データを物理的に削除するのではなく、データに `deleted: true` フラグを立てる**論理削除（Soft Delete）**として実行する。
* **読み込みのリアルタイム・ハイブリッド化（`fetchMarkers` 処理）**:
    * アプリ起動時のマーカー取得処理（`fetchMarkers`）は、以下の2つのデータ取得を**並行して実行**する。
        1.  **ベースデータ (JSON)**: 高速な静的ファイル **`markers.json`** を読み込む。（前日の定時バッチで生成された確定データ）
        2.  **リアルタイム差分データ (Firestore onSnapshot)**: Firestoreに対し、`markers.json` ファイルの**「最終更新日時」以降**に `updatedAt` フィールドが変更されたデータのみを、**Firestoreのリアルタイムリスナー (`onSnapshot`)** で監視する。
    * **データマージと反映**:
        * クライアントはベースデータ取得後、**リアルタイムリスナーの監視を開始**する。
        * リスナーが受け取った変更データ（新規登録、更新、削除フラグ）を、クライアント側のデータセットに即座に反映し、地図を更新する。
        * **利点**: 読み取るドキュメント数は「差分」のみになり、APIコストを最小限に抑えつつ、自己/他者の登録が即座に反映される。
* **定時バッチ処理の役割**:
    * `1.3. バックエンド処理` で定義されている毎日00:00 JSTの定時バッチ処理は、データベースの全件データに基づき、**`deleted: true` のレコードを除外**した**最新の全マーカーデータ**を格納した **`markers.json` を再生成**する役割を担う。

## Loca での扱い（移植時の差分）

移植元は Firebase と Google Maps を前提にしていた。Loca は配信先未定のため、
要件の**意図は保ったまま、実現手段を差し替え可能にした**。差分は以下のとおり。

| 元の要件 | Loca での実現 | 根拠 |
|---|---|---|
| 認証は Google 認証のみ | 維持。`AuthPort` の実装は `src/adapters/firebase/auth.ts`（Google 認証）だけ。移植時にあった疑似ログインの `local` は廃止した | 構成を Firebase に確定したため（ADR 0010） |
| `.env` の変数名（`VITE_COMMON_API_KEY` 等） | `.env.example` の体系に置き換え。共通キーの使い回しはやめ、サービスごとに分離 | 1 つのキーの漏洩で全サービスが巻き添えになるのを避けるため |
| API はできるだけサーバー側で呼ぶ | 静的配信のみでも成立するよう、まずクライアント実装。サーバー側の実装は配信先決定後に追加できる形にした | 現時点でサーバーを前提にできないため |
| バンドルはチャンク 500kB 以内 | 維持。`vite.config.ts` の `manualChunks` でベンダを分割し、未使用アダプタは動的 import でロードしない | — |
| Google Maps はメインバンドルに含める | MapLibre を既定にし、地図ライブラリは独立チャンク（動的 import）に変更 | 地図エンジンを差し替え可能にするため |
| 定時バッチは cron / Firebase Functions | GitHub Actions（`sync-firestore.yml`）が毎日 0:00 JST に Node のスクリプトを動かす | Cloud Functions は請求先が必須で使えないため |
| （同上）動かすスクリプト | `scripts/refresh-youtube.mjs`・`sync-firestore.mjs`・`purge-deleted.mjs` | 同上 |
| `markers.json` ベース + Firestore 差分 | 維持。ベースは `public/data/markers.json`、差分は `MarkerStorePort.subscribeChanges` の購読（ADR 0013）。バックエンドが落ちればベースだけで縮退運転する | 可用性の要求に直結するため |
| レートリミット（IP あたり 10 回/分） | 利用者単位をセキュリティルールで実装。マーカーを書くバッチ（といいねを付ける書き込み。ADR 0024）で `rateLimits/{uid}` の印を更新させ、直前から 6 秒以上あいていないと拒否する（ADR 0012）。**IP 単位の遮断は未実装** | 静的配信では IP を判定できない。配信先の WAF で行う |

### 未実装として明示するもの

- **IP 単位のレートリミットとアクセス遮断**: 作らない。静的配信では IP を判定できない。遮断はホスティング側の責務。
- **サーバー側 API プロキシ**: 現時点ではクライアントから直接外部 API を呼ぶ。
- **App Check / reCAPTCHA**: 使わない。reCAPTCHA が支払い方法の登録を求めるため。代わりにブラウザ用の API キーを HTTP リファラーで絞る（ADR 0030）。

## 追記（2026-09-22 の構成確定）

1.1 の認証要件と 1.3 のバックエンド要件は、構成確定にともない次のように変わった。

| 本章の記述 | 現在 |
|---|---|
| 1.1 Google 認証 | **廃止**。投稿時の GitHub アカウントが本人確認を兼ねる |
| 1.1 プロフィール登録・同意履歴 | Issue フォームの必須チェックに移管。サイト側は保持しない |
| 1.1 管理者モード | 統計とエクスポートのみ公開機能として残す。それ以外は GitHub 上の操作 |
| 1.2 .env の変数定義 | `project/.env.example` に置き換え。API キーは 1 つも使わない |
| 1.3 定時バッチ | Issue 取り込み（`ingest-issue.yml`）に置き換え |
| 1.3 レートリミット | GitHub 側の制限に委ねる。アプリ内実装は削除 |
| 1.4 ベース JSON ＋ リアルタイム差分 | **ベース JSON のみ**。差分購読の相手（DB）が無い |
